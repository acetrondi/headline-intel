# Contributing

## The one rule

`pipeline/features.py` and the extractor in `assets/app.js` are the **same function in two
languages**. If you change one, change the other, and run:

```bash
python3 pipeline/verify.py
```

It compares all 45 features across 40 real titles and fails on any mismatch. CI runs it on
every push, so a drift will not merge.

## Adding a data source

1. Drop raw payloads in `raw/` as `<url>\n\n<body>` (or point `HI_RAW_DIR` elsewhere).
2. Write an adapter in `pipeline/harvest.py` that yields `rec(...)` records.
3. Register it in the dispatcher inside `main()`.
4. Add an engagement floor to `FLOORS` in `pipeline/normalize.py`.
5. Re-run the pipeline (see README), then `pipeline/build_data.py`.

**Choose the floor deliberately.** Too low and the model learns what makes a mediocre post
slightly less mediocre. Too high and there is no variance left to learn from. Aim for a real
success threshold with the full range above it intact.

## Adding a feature

Features must be **deterministic, cheap and countable** — a property of the string, not a
model output. That is what makes the score auditable and the app dependency-free. Add it to
`title_features()` in both languages, then refit:

```bash
python3 pipeline/model.py && python3 pipeline/build_data.py && python3 pipeline/verify.py
```

## Claims must be reproducible

Numbers in `docs/` are generated by `pipeline/report.py` from `data/analysis.json`, so prose
cannot drift from data. Don't hand-edit `docs/` — change the generator.

If you add a claim to the README, make sure a script produces it.

## Style

No frameworks, no build step, no bundler. Plain HTML, CSS and ES2020. The site must keep
working when opened from disk with `file://`.
